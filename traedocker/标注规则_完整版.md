# 环境 & prompt & traj 标注标准（完整版）

> 来源：飞书文档《环境 & prompt & traj 标注标准》+ 《标注补充要求》
> 最后更新：2026-06-02（文档更新时间）

---

## 1. 任务描述与目标

### 1.1 任务目标

本任务要求围绕真实代码仓库构建可复现环境，并基于同一环境采集多条真实用户 prompt。每条 prompt 需要在 **Trae 平台中打开对应容器**后进行 5 次独立运行，并记录每次运行的 session 信息、模型信息、评分结果、评分理由以及 git diff 产物。

核心目标包括：
1. 收集可在 Trae 中打开并运行的**真实**代码仓库环境
2. 基于同一套环境采集 **5～20 条**真实用户 prompt
3. 对每条 prompt 在 Trae 中进行 **5 次独立 rollout**
4. 每次 rollout 结束后记录 `session_id`、`model_name`、`score`、`score_reason`，并上传 git diff 产物文件

### 1.2 数据组织方式（三级结构）

本任务在飞书多维表中采用三级结构：

| 层级 | 说明 |
|------|------|
| **仓库级父记录** | 记录仓库、Dockerfile、repo 初始文件等环境信息 |
| **Prompt 级一级子记录** | 记录基于该仓库环境设计的用户 prompt 及任务元数据 |
| **Rollout 级二级子记录** | 记录每条 prompt 的单次 Trae 运行结果 |

关系：
- 一个仓库级记录对应 5～20 条 prompt
- 一条 prompt 对应多条 rollout 记录
- 一条 rollout 记录对应一次在 Trae 中打开容器后的**独立单 session 运行**

### 1.3 标注职责

1. 准备并上传 Dockerfile
2. 上传 repo 初始文件压缩包
3. 填写仓库级环境信息
4. 基于该仓库环境编写真实用户 prompt
5. 标注 prompt 的难度、类别、技术栈和功能模块
6. 在 Trae 中打开容器，并基于该容器执行 rollout
7. 记录每次 rollout 的 `session_id`、`model_name`、`score`、`score_reason`
8. 每次 rollout 结束后执行 `git diff`，将结果转存为 patch 文件并上传到飞书表附件字段

### 1.4 Trae 容器运行要求

所有 rollout **必须在 Trae 中打开对应容器后执行**，不得使用本地环境、普通终端环境或其他未指定环境替代。

标注人员需确保：
1. 使用的是当前仓库记录对应的 Docker 环境
2. Trae 中打开的容器代码现场与任务初始现场一致
3. **每次 rollout 均从同一初始现场开始**
4. **每次 rollout 均为独立单 session**

### 1.5 模型使用要求

5 次 rollout 需要在 Trae 中进入 PPE，并使用以下模型进行 rollout：

**GPT5.4，Gemini 3.1 pro，DeepSeek-v4，Doubao-Seed-2.0-Code，MinMax-M2.7/GLM-5.1/Qwen3.6-Plus**

执行顺序要求：
- **前四次 rollout** 需按照 GPT5.4 → Gemini 3.1 pro → DeepSeek-v4 → Doubao-Seed-2.0-Code 的顺序依次进行
- **每一个 prompt 的第五次 rollout** 按照 MinMax-M2.7/GLM-5.1/Qwen3.6-Plus 这个顺序**轮流**选择进行

> 如果模型跑的过程中有问题，就在群里同步，**不能私自更改模型**。

### 1.6 Prompt 设计与分数覆盖要求

本任务采集的 prompt 不仅需要基于真实仓库上下文，还需要具备一定的任务层次和模型区分度。在设计 prompt 时，应尽量**覆盖不同难度、不同模块、不同任务类型**，避免所有 prompt 都集中在简单局部修改、纯文档补充或高度重复的问题上。

每条 prompt 完成 5 次独立 rollout 后，根据该 prompt 下 5 个 rollout 的真实 score 结果，判断该 prompt 的分数覆盖类型。**不允许为了满足分布要求修改真实评分。**

#### 1.6.1.1 prompt 基本要求

每条 prompt 应满足以下要求：
1. 必须基于当前仓库的真实代码上下文设计
2. 问题应具体、可执行，避免"优化一下项目""看看哪里有问题"这类目标过泛的表达
3. prompt 中应尽量包含明确的任务目标、涉及模块、期望行为或验证方式
4. 可以是代码修改类任务，也可以是仓库相关的理解、分析、解释或问答类任务
5. 问答类任务必须与当前仓库的代码实现、模块设计、运行现象、工程配置或使用方式直接相关，不得设计为脱离仓库上下文的泛知识问题
6. 同一仓库下的 prompt 不得高度重复，应覆盖不同功能模块、不同任务类型或不同复杂度
7. **prompt 必须能够在当前 Docker / Trae 容器环境中执行，不得依赖当前环境不支持的能力**
8. 不得设计恶意、不可完成、故意模糊或与仓库无关的问题

#### 1.6.2 prompt 分数覆盖类型

每条 prompt 需要使用 5 个模型各独立 rollout 一次。根据 5 次 rollout 的真实 score 集合，将 prompt 分为以下三类：

| 类型 | 目标占比 | 判断方式 | 说明 |
|------|---------|----------|------|
| A 类：强区分 prompt | 约 15% | 5 次 rollout 覆盖 0/1/2 三个分数 | 不同模型结果差异明显 |
| B 类：中区分 prompt | 约 50% | 5 次 rollout 覆盖恰好两个分数 | 不同模型有一定差异，是主要 prompt 类型 |
| （其余） | 约 35% | — | — |

示例：
```
A 类：0, 1, 2, 2, 1
B 类：1, 1, 2, 2, 2
B 类：0, 0, 1, 1, 1
```

注意：
1. 上述比例按标注人员或批次累计结果统计，不要求单个仓库严格满足
2. 单个仓库的 prompt 数量为 5～20 条，只需尽量保证 prompt 类型多样
3. 最终 prompt 类型以 5 个 rollout 的真实 score 结果为准
4. **不得为了让 prompt 落入某一类型而修改 score**
5. 如果实际结果与预期不一致，以真实结果为准，后续通过补充 prompt 调整整体分布

#### 1.6.3 禁止事项

标注人员需特别注意：
1. 不得为了满足分数覆盖比例修改真实 score
2. 不得在看到模型结果后反向调整 prompt，并将原 rollout 结果挂到调整后的 prompt 下
3. 如果 prompt 内容发生实质修改，需要**重新执行该 prompt 下的 5 次 rollout**
4. 不得故意设计无法完成、目标不清、脱离仓库上下文的问题
5. 不得通过重复相似 prompt 批量填充数量
6. Score 必须根据 prompt 目标、模型执行过程、最终代码状态、git diff 和评分标准如实填写

**最终要求：prompt 设计应真实、具体、可执行，并尽量具备区分度；分数结果必须真实记录，不得人为调整。**

## 2. 字段描述

### 2.1 仓库级字段

仓库级字段对应多维表中的父记录，一条记录代表一套共享环境。

| 字段名 | 必填 | 说明 |
|--------|------|------|
| repo_url | 是 | 仓库地址或来源信息 |
| repo_type | 是 | 仓库属性：私有仓库 / 公有仓库 |
| language | 是 | 仓库主要使用的编程语言 |
| dockerfile | 是 | 上传的 Dockerfile 附件 |
| repo | 是 | repo 中项目的初始文件，使用压缩包提交 |
| environment_notes | 否 | 环境补充说明 |
| task_count | 是 | 当前仓库下 prompt 数量，要求 5～20 条 |

### 2.2 Prompt 级字段

Prompt 级字段对应仓库级记录下的一级子记录，一条记录代表一条用户 prompt。

| 字段名 | 必填 | 说明 |
|--------|------|------|
| prompt_index | 是 | 任务序号 |
| prompt | 是 | 真实用户在 Agent 中输入的原始请求 |
| difficulty | 是 | 任务难度，按附录评分规则标注相应难度分级 |
| category | 是 | 任务类别，按附录类型表选择对应任务类型 |
| tech_stack | 是 | 技术栈标签，按照需求产物填写；多个值用逗号分隔 |
| module_tags | 是 | 功能模块标签，按照需求产物填写；多个值用逗号分隔 |

### 2.3 Rollout 级字段

Rollout 级字段对应 prompt 下的二级子记录，一条记录代表一次在 Trae 中打开容器后的独立运行。

| 字段名 | 必填 | 说明 |
|--------|------|------|
| rollout_id | 是 | rollout 编号（填写 1～5，按 session id 时间顺序来排） |
| session_id | 是 | 本次 Trae 运行的会话 ID |
| model_name | 是 | 本次运行使用的模型名称 |
| score | 是 | 评分（0/1/2） |
| score_reason | 是 | 评分理由 |
| git_diff | 是/否 | patch 文件附件（若无代码修改则上传空 patch 或说明文件） |
| notes | 否 | 异常说明（如 Trae 打开失败、session 中断等情况在此说明） |

## 3. 标注流程

### 3.1 创建仓库级记录

标注人员首先在多维表中创建仓库级父记录，并填写以下字段：
- repo_url、repo_type、language、dockerfile、repo、environment_notes、task_count

仓库环境应满足：
- **必须是日常开发使用的**
- 具备真实开发上下文
- 代码结构足以支撑至少 5 条任务
- 可以在 docker 中构建和复现
- 不建议选择过于空泛、纯 demo、过小或无法运行的仓库
- **如果是纯 demo 项目，题目会直接废弃，不结算**

### 3.2 准备 Dockerfile 与 repo 压缩包

标注人员需准备并上传：
1. **Dockerfile 附件**
2. **repo 初始文件压缩包**

环境准备要求如下：
1. Dockerfile 中必须设置 `WORKDIR /app`
2. **容器内仓库目录统一为 `/app`**
3. 必须确保容器内仓库状态为 Agent 处理任务前的初始现场
4. 若当前仓库快照不是目标现场，应在 Dockerfile 中直接 checkout 到正确现场
5. 所有项目都必须完成 Git 初始化
6. Dockerfile 需完成最小可用初始化，包括安装必要依赖、创建工作目录、预留 app 目录，并提供默认 shell 或默认命令（可选）

**Docker 特别要求（⚠️ 必须遵守）：**
- 统一版本：`Docker version 29.4.2, build 055a478`
- **不允许使用 DinD、docker compose**，遇到需要使用的应该更换仓库
- **不允许用清华源**
- 构建的仓库需要统一为 `repo` 文件夹就是项目文件夹，下面不要有子的项目文件夹（目前的逻辑是 repo 下面是单独的文件夹就会把对应文件夹的内容抽取出来放到 repo 里面）
- dockerfile 的路径也需要这么去写，不然可能复现起来会有报错

### 3.3 验证环境可用性

环境准备完成后，需进行自检，要求如下：
1. Docker 镜像可成功构建
2. 容器可正常启动
3. 当前工作目录为 `/app`
4. `/app` 中已包含任务相关代码内容
5. `/app` 已完成 Git 初始化，并且是一个可用的 Git 仓库
6. 容器内代码即为任务起始现场，无需额外 checkout 或手工准备
7. 进入容器后无需额外手工初始化即可开始工作
8. 环境可在 Trae 中正常打开

**特别要求：** 后续 rollout 必须基于 Trae 中打开的该容器执行。环境仅能本地构建成功不代表满足 rollout 要求，必须确认可在 Trae 中打开和使用。

### 3.4 采集 Prompt

围绕该仓库设计 5～20 条任务（基于原始仓库设计难度），并创建对应子记录。

任务设计要求：
- prompt 必须要确保在给定的 docker 环境中是可运行的问题（不支持 DinD）
- 尽量模拟真实用户在 Agent 中的表达方式
- 应建立在当前仓库真实代码上下文之上，题目中最好涉及到/引用到原始代码片段，保证分布足够真实

### 3.5 标注 Prompt 元数据

每条 prompt 需补充任务元数据：
1. `difficulty`：按附录 A 的难度规则标注
2. `category`：按附录 B 的任务类型定义义选择
3. `tech_stack`：填写涉及的技术栈，多个值可用逗号分隔
4. `module_tags`：填写涉及的功能模块，多个值可用逗号分隔

填写要求：
1. 难度应根据任务本身的需求清晰度、修改或分析范围、环境复杂度、验证复杂度综合判断
2. 类别按任务主要目标择单一类型
3. 技术栈和功能模块只用于描述任务涉及的技术或模块，不填写难度、类别、评分等信息
4. 多个标签可使用中英文逗号分隔，后续由项目侧统一清洗处理

### 3.6 在 Trae 中打开容器并执行 Rollout

每条 prompt 完成后，需在 Trae 中打开当前仓库对应容器，并基于该容器执行 rollout。

执行要求如下：
1. 每次 rollout **必须在 Trae 中打开目标容器后执行**
2. 每次 rollout 均**从相同初始代码现场开始**
3. 不得在本地环境或其他未指定环境中替代执行
4. 每rollout从【】五个模型中选择，每个模型各一次。**注意：一个 prompt 需要使用不同模型跑五次，需要单开五个任务，不能在一个会话里换模型跑五次**
5. 每次运行结束后，记录本次运行的 `session_id`
6. 每次运行结束后，记录本次运行使用的 `model_name`
7. 每次运行结束后，保留运行后的代码现场，用于提取 `git diff`
8. 如 Trae 打开容器失败、session 异常中断或无法继续运行，应在 rollout 记录的 `notes` 中说明

### 3.7 提取 git diff 并上传

每次 rollout 结束后，需在运行后的代码现场执行 `git diff`。

操作要求如下：
1. 使用运行后的代码现场生成 diff
2. 将 `git diff` 结果转存为 patch 文件
3. 将 patch 文件上传到 rollout 级记录的 `git_diff` 附件字段
4. 确保上传的 patch 文件与当前 rollout 记录一一对应
5. 若本次运行未产生代码修改，也需要上传空 patch 或说明文件，并在 `notes` 中说明原因

建议文件命名：`{rollout_id}.patch`

### 3.8 评分与填写理由

每次 rollout 结束后，标注人员需要对运行结果进行评分。

评分取值如下：

| 分数 | 定义 |
|------|------|
| 0 | 未完成任务，结果明显错误，或无法形成有效产物。体感很差。 |
| 1 | 任务已经完成，但是用户体感不行（有额外的操作或修改了不应修改的文件）。 |
| 2 | 任务完美执行，用户体感良好。 |

填写要求：
1. 评分理由应说明本次运行为什么得到该分数
2. 评分应结合 prompt 目标、运行过程、最终结果和 `git_diff` 内容判断
3. 如果由于资源或是工程问题导致的输出中断，需要进行重试，只提交运行成功的结果

### 3.9 提交前自检

提交前需确认：
1. 仓库级字段均已填写完整
2. Dockerfile 附件已上传
3. repo 初始文件压缩包已上传
4. 当前仓库下 prompt 数量为 5～20 条
5. 每条 prompt 均已填写 `prompt_index` 和 `prompt`
6. 每条 prompt 均已填写 `difficulty`、`category`、`tech_stack`、`module_tags`
7. 每条 prompt 已完成规定次数的 rollout
8. 每条 rollout 均在 Trae 中打开容器后执行
9. 每条 rollout 均已填写 `session_id`、`model_name`、`score` 和 `score_reason`
10. 每条 rollout 均已上传 `git_diff` 附件，或在 `notes` 中说明无 diff 原因

## 4. 其他要求

1. **Docker 统一版本**：`Docker version 29.4.2, build 055a478`
2. **不允许使用 DinD、docker compose**，遇到需要使用的应该更换仓库
3. **不允许用清华源**
4. 构建的仓库需要统一为 `repo` 文件夹就是项目文件夹，下面不要有子的项目文件夹
5. 每一条 prompt，需要跑五个模型，每个模型都需要**单开一个会话**；7 条 prompt 应该有 35 个会话窗口。目前发现有好多同学只开五个会话窗口，session ID 调出轨迹后发现多轮对话，不符合规则，抽检发现后将全部打回重新作业，情况严重的会剔除作业名单。

## 5. 附录

### 附录 A：难度定义

#### A.1 评分维度表

| 维度 | 0 分 | 1 分 | 2 分 |
|------|------|------|------|
| 需求清晰度 | 目标非常明确，几乎不需要推断 | 目标基本明确，但有少量需要判断的地方 | 目标模糊，存在多种理解或实现路径 |
| 修改范围 | 单文件或局部改动 | 多文件改动，但范围可控 | 跨模块、跨层级或全仓库联动 |
| 环境与依赖复杂度 | 基本不依赖复杂环境，直接可推进 | 需要跑测试、起服务、看日志等基础操作 | 依赖复杂环境、外部服务或工程配置障碍 |
| 验证复杂度 | 一步即可验证结果 | 需要多步验证或组合验证 | 验证链路长，回归影响面大 |

**难度打分 = 4 个维度得分之和**

#### A.2 难度映射表

| 总分 | 说明 |
|------|------|
| 0～2 | 简单 |
| 3～5 | 中等 |
| 6～8 | 困难 |

### 附录 B：任务类别定义

| 名称 | 定义 | 典型输入 | 典型输出 |
|------|------|----------|----------|
| 代码生成 | 从需求描述出发，从零生成可运行的项目或模块 | PRD / 功能描述 | 可运行的项目代码 |
| Bug 修复 / 调试 | 从 issue 或报错信息出发，定位并修复问题 | Bug 报告 / Stack trace / Failing test | 修复后的代码 + 回归测试 |
| 代码重构 | 改善代码结构、性能或可维护性，行为保持不变 | 重构目标描述 + 现有代码库 | 重构后的代码 |
| 功能迭代 | 在已有代码库上添加或修改功能 | 功能需求 + 现有代码库 | 新增 / 修改的代码 |
| 测试 | 为已有代码编写全测试用例 | 待测代码 | 测试代码 |
| 代码理解与分析 | 阅读代码并给出解释、审查意见或分析报告 | 代码库 / PR diff / 分析问题 | 结构化分析结果 |
| DevOps / 工程化 | 配置 CI/CD、Docker、部署方案等工程建设 | 项目代码 + 工程化需求 | 配置文件 / 脚本 |

### 附录 D：Dockerfile 示例

#### D.1 Linux dockerfile

```dockerfile
# 基础镜像（自定义，可选择一个最合适当前项目的 base image）
FROM ubuntu:22.04

# 设置工作目录
WORKDIR /app

# 把宿主机当前目录下 xxx 仓库文件夹内的"所有内容"复制到容器的 /app 目录下
COPY xxx/ ./

# （可选）安装必要环境等操作
RUN apt-get update && apt-get install -y --no-install-recommends \
    tmux \
    git \
    curl \
```

## 6. 补充要求（标注补充要求文档）

### 6.1 仓库部分（细节注意）

仓库选择必须遵循以下规则：
- **必须是日常开发使用的**
- 具备真实开发上下文
- 代码结构足以支撑至少 5 条任务
- 可以在 docker 中构建和复现
- 不建议选择过于空泛、纯 demo、过小或无法运行的仓库
- **如果是纯 demo 项目，题目会直接废弃，不结算**

### 6.2 Prompt 部分（细节注意）

- 只有 seed 做不对的 prompt 对我们来说才是有价值的
- **大家在跑模型时优先跑 seed（Doubao-Seed-2.0-Code）**，只有 seed 为 0 分的 prompt，才能去跑其他模型，如果 seed 未达到 0 分，就需要修改或废弃这条 prompt（除了"代码阅读理解与分析"类型）

**最新要求（20260528）：**
- 每个题目要求 7 轮 prompt，包含一轮**代码阅读理解与分析** prompt（没有 git diff 那种）和另外 6 轮其他类型
- 在跑模型时优先跑 seed，**只有 Doubao-Seed-2.0-Code 为 0 分的 prompt**，才能去跑其他模型，如果 seed 未达到 0 分，就需要修改或废弃这条 prompt（除了"代码阅读理解与分析"类型）

### 6.3 评分部分（细节注意）

- score 打分除了"代码阅读理解与分析"类型的题目可以存在全 2 分之外，其他类型的 prompt **不允许出现全部 2 分的情况**，如果出现全 2 分的情况就需要修改 prompt，重新跑 trae。（关于"代码阅读理解与分析"类型：每个仓库对应的 prompt 中最多只允许出现一个这种文档撰写类型的 prompt）
- **Score 的打分是对模型本身能力的打分**，如果是因为报错/长时间循环输出/等待时间过长，这些是工程链路上的问题，不能作为打分依据

### 6.4 Rollout 模型要求（细节注意）

5 次 rollout 需要在 Trae 中进入 PPE，并使用以下模型进行 rollout：
- GPT5.4，Gemini 3.1 pro，DeepSeek-v4，Doubao-Seed-2.0-Code，MinMax-M2.7/GLM-5.1/Qwen3.6-Plus

要求：
- **前四次 rollout** 需要按照 GPT5.4，Gemini 3.1 pro，DeepSeek-v4，Doubao-Seed-2.0-Code 四个模型的顺序依次进行
- 每一个 prompt 的**第五次 rollout** 按照 MinMax-M2.7/GLM-5.1/Qwen3.6-Plus 这个顺序轮流选择进行
- 如果模型跑的过程中有问题，就在群里同步；如果问题短期不能修复，项目方会通知更换模型，不能私自更改模型。

**rollout id 填写 1～5，patch 名称填写 1～35，rollout 行需要按照 session id 的时间顺序来排**

### 6.5 问题解答

#### Q1: 如果模型没有进行操作修改怎么办？
可以上传空 patch 文件，并在打分原因中说明（除模型生成文本类型的需求）。

#### Q2: 产物命名怎么制定？
可以自定义，不过要求必须是 `.patch` 文件，我们这边统一处理。

#### Q3: prompt 初始状态，是否可以保存上一个 prompt 的最后一个模型的修改，然后基于此进行下一个 prompt 的 5 轮 rollout？
**禁止**，prompt 之间不能相互依赖，**每一个 prompt 都必须基于仓库初始状态编写**。

#### Q4: 遇到模型思考次数达上限的问题应该怎么办？
这部分是之前 gpt5.4 的 context 配置有问题，目前已经进行了修复，可以再重试试。如果还遇到的话可以让模型继续。并**以最后一轮 session id 作为 session id**。

#### Q5: 关于 rollout 的干净度要求
每一次都需要是干净的 rollout，除了模型本身的问题（比如输出超长，可以点继续，session id 使用新的那一条的 session id）。工程问题，比如链接失败、模型错误，需要重建容器，重新运行，保证测试是**从同一个 base 完成的干净 rollout**。

#### Q6: 禁止使用 Trae 隐私模式
大家注意检查一下 Trae CN 的设置，一定要**关闭 TRAE 的隐私模式**！如果之前有同学打开了隐私模式，甲方是提取不到轨迹数据进行验收的。当时甲方要求将**所有数据作废**（不仅作废关闭时的数据，是所有数据作废），并且不允许再参加项目进行作业。如果之前有提交的数据打开了隐私模式，自己将其废弃重做。

## 7. 快速参考卡

### 模型顺序（每条 prompt，实际操作顺序）
| 执行顺序 | Rollout 编号 | 模型 |
|---------|-------------|------|
| **①** | 1 | **Doubao-Seed-2.0-Code（seed，优先跑，决定 prompt 是否有效）** |
| ② | 2 | GPT-5.4 |
| ③ | 3 | Gemini 3.1 pro |
| ④ | 4 | DeepSeek-v4 |
| ⑤ | 5 | MinMax-M2.7 / GLM-5.1 / Qwen3.6-Plus（每个 prompt 轮流） |

> ⚠️ **必须先跑 Doubao（seed）**：确认为 0 分后才能跑其他模型。如果 Doubao 不是 0 分，需要修改或废弃 prompt（代码阅读理解类除外）。

### 每条 prompt 的工作流程
```
1. 在 Trae 中打开仓库对应的 Docker 容器
2. ❶ 先用 Doubao-Seed-2.0-Code 跑 → 如果不是 0 分，修改或废弃 prompt
3. 确认 seed 为 0 分后：
   ❷ GPT-5.4 → ❸ Gemini 3.1 pro → ❹ DeepSeek-v4 → ❺ 轮换模型
4. 每次跑完：记录 session_id → git diff → 转成 .patch → 上传 → 填写 score + reason
5. 每次 rollout 都要从同一初始代码现场开始（干净容器）
```

### 评分标准快查
| 分数 | 含义 |
|------|------|
| **0** | 任务失败，结果明显错误，无有效产物，体感差 |
| **1** | 任务完成但有瑕疵（多余操作/修改了不该改的文件），体感不好 |
| **2** | 任务完美完成，体感良好 |

> ⚠️ 非阅读理解类型：不允许 5 次全部 2 分！出现要改 prompt 重跑。
> ⚠️ Score 是模型能力评分，工程链路问题（报错/超时/循环）不算在内。

### 容易犯错的红线
| 违规行为 | 后果 |
|----------|------|
| 一个会话跑多个模型 | 全部打回重做，严重者剔除名单 |
| 开启 Trae 隐私模式 | 所有数据作废，不得再参与项目 |
| 不同 prompt 基于上一个 prompt 的修改 | 违规，必须每次从仓库初始态开始 |
| 提交纯 demo 项目 | 题目直接废弃，不结算 |
| 使用清华源 / DinD / docker compose | 违规 |
| 私自更改模型 | 违规 |
| 为满足分布比例改 score | 严重违规 |
